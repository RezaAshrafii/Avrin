# دستور اجرایی کامل ساخت دموی اختصاصی هتل اورین

نسخهٔ ۱٫۰ — ۲۱ اکتبر ۲۰۲۶ — زبان رابط: فارسی و راست‌به‌چپ — مخاطب: مدل مجری با توان متوسط؛ بازبینی نهایی با مدل قوی‌تر و ناظر انسانی.

> **این فایل قرارداد اجرایی دمو است.** یک سایت قابل اجرا و قابل کلیک بساز. تمام صفحه‌ها و حالت‌های الزامی زیر را پیاده کن. برای تصمیم‌هایی که این فایل مشخص کرده، از سلیقهٔ پیش‌فرض، قالب آماده، عکس تصادفی یا محتوای ساختگی استفاده نکن. مقدارهای طراحی این فایل، تصمیم اختصاصی پروژهٔ اورین‌اند و اندازه‌گیری CSS سایت‌های مرجع محسوب نمی‌شوند.

## راه استفاده از این دستور

ابتدا بخش‌های ۱ تا ۶ را کامل بخوان؛ سپس به ترتیب بسته‌های اجرایی بخش ۲۰ کار کن. جدول‌های پیوست، نقشهٔ قطعی داده و عکس هستند. فایل‌های اصلی را بازنویسی نکن. در پایان هر بسته، وضعیت انجام و موارد باقی‌مانده را در `IMPLEMENTATION_STATUS.md` ثبت کن و به بستهٔ بعدی برو. سؤال‌های غیرضروری دربارهٔ رنگ، چیدمان، مسیر یا فناوری نپرس؛ این تصمیم‌ها در همین فایل آمده‌اند. در صورت نبود یک دادهٔ واقعی، طبق رفتار جایگزین مشخص‌شده عمل کن و آن را در `CONTENT_REVIEW.md` ثبت کن.

تحویل این مرحله: سورس پروژه، نسخهٔ محلی اجراشدنی، تمام مسیرهای الزامی، دادهٔ محلی منو، تصاویر بهینه‌شدهٔ مجاز، و گزارش کوتاه بازبینی. انتشار عمومی، اتصال درگاه و اتصال رزرو مرحلهٔ دیگری است.

فهرست بخش‌ها: ۱ هدف؛ ۲ مرجع و کاستوم‌سازی؛ ۳ فایل‌های ورودی؛ ۴ قرارداد تصویر؛ ۵ سیستم بصری؛ ۶ مسیرها؛ ۷ پوسته؛ ۸ خانه؛ ۹ اتاق‌ها؛ ۱۰ رزرو؛ ۱۱ رستوران؛ ۱۲ منو؛ ۱۳ سبد؛ ۱۴ گالری؛ ۱۵ صفحه‌های تکمیلی؛ ۱۶ قرارداد داده؛ ۱۷ فنی؛ ۱۸ دسترس‌پذیری و کارایی؛ ۱۹ حالت‌ها و متن؛ ۲۰ ترتیب اجرا؛ ۲۱ پذیرش؛ ۲۲ دستور بازبینی؛ سپس پیوست‌های داده و عکس.

## ۱. هدف محصول و حدود صداقت محتوا

اورین یک هتل شهری در محدودهٔ انقلاب تهران است و رستوران و کافه دارد. تجربهٔ طراحی باید «اقامت شهری باوقار، دسترسی روشن و غذا در یک مجموعهٔ واقعی» را منتقل کند. عکس‌های واقعی دارای دکور چوبی، رنگ‌های سبز تیره، جزئیات طلایی، پذیرش و فضای رستوران هستند. همین ویژگی‌ها زبان بصری طراحی را می‌سازند.

دو هدف اصلی کاربر: پیدا کردن اتاق مناسب و طی‌کردن رزرو نمایشی؛ پیدا کردن غذا و طی‌کردن سبد نمایشی. مسیر تماس و مسیریابی در تمام صفحه‌ها در دسترس باشد.

عنوان هتل «هتل اورین تهران» و نام کوتاه «اورین» است؛ آن را در یک فایل پیکربندی متمرکز نگه دار تا تغییر احتمالی به «آورین» ساده باشد. پسوند HOTEL برای wordmark لاتین مجاز است. هیچ ستاره، جایزه، رتبه، درصد رضایت، تعداد مهمان، قدمت، فاصلهٔ دقیقه‌ای یا ادعای خدماتی تازه نساز. استخر، اسپا، ساحل، ویلا، سرآشپز مشهور، رویداد یا خدمات لوکس مراجع را به اورین نسبت نده.

داده‌ها snapshot عمومی زمان استخراج‌اند. یک نشان کوچک «نسخهٔ نمایشی» در رابط باشد و در فرم‌ها توضیح کوتاه «رزرو و سفارش نهایی در این پیش‌نمایش انجام نمی‌شود.» نمایش داده شود. متن فنی دربارهٔ API، مدل AI، وردپرس یا الگوریتم تشخیص عکس وارد تجربهٔ مهمان نشود.

## ۴. قرارداد قطعی عکس و انتخاب دارایی

### ۴٫۱ عکس محصول

شرط لازم: `use_image_in_demo === true` **و** `image_demo_status === 'real_product_photo'` **و** مسیر معتبر موجود در `image_files`. اگر هر شرط برقرار نبود، `image=null` تولید کن. این شرط باید در مرحلهٔ import و در تابع renderer اعمال شود. در `onError` هم به حالت بدون عکس برگرد؛ هیچ URL پیش‌فرضی قرار نده.

hash محتوای عکس عمومی ممنوع: `7bad8283e602e2d7dd6e7252db6d9160abcab07e85bd7ec3472c13ca4363ed19`. ۱۶۶ محصول این فایل یکسان را داشتند. تمام فایل‌های `_quarantine_generic_placeholder` از import، کپی به public، گالری و پیشنهادهای تصویر حذف شوند. تصاویر آیکون دستهٔ سرویس منو هم برای hero، کارت غذا و گالری ممنوع‌اند.

۱۰ رکورد دیگر عکس واقعی مشترک دارند و تا تطبیق انسانی `use_image_in_demo=false` می‌مانند. برای تصویری که مجاز نیست، محصول را حذف نکن؛ کارت متنی طراحی کن. عکس استیک مرغ فقط به محصول `97818111` تعلق دارد. محصول `195061748` عکس مجاز ندارد. در سراسر پروژه این دو نمونه باید رفتار متفاوت داشته باشند.

در متن فارسی `letter-spacing` صفر باشد. تلفن، ایمیل، slug و کدها `<bdi dir="ltr">` داشته باشند. فقط یک H1 برای هر صفحه. کلمهٔ AV RIN را تغییر نده؛ wordmark تایپوگرافیک نمایشی `AVRIN` و «اورین» باشد، نه بازسازی تصویری لوگوی رسمی.

### ۵٫۳ شبکه، اندازه و سطوح

Desktop >=1200: container حداکثر ۱۲۸۰ px، gutter ۴۸ px، شبکهٔ ۱۲ ستون و gap ۲۴ px. Tablet 768..1199: gutter ۳۲ px، gap ۲۰ px. Mobile <768: gutter ۲۰ px، gap ۱۶ px. در ۳۶۰ px gutter ۱۶ px مجاز است. بخش‌های full-bleed از container بیرون می‌روند ولی متن آن‌ها با حاشیهٔ داخلی هم‌راستا می‌شود.

فاصلهٔ عمودی section در desktop ۱۰۴ px و mobile ۶۴ px؛ بین عنوان و متن ۲۰ px؛ پیش از CTA بیست‌وهشت px. کارت تصویرها radius صفر تا ۴ px؛ panel فرم ۸ px؛ chip فیلتر radius ۹۹۹ px فقط برای کنترل فیلتر. ارتفاع دکمه ۴۸ px desktop و ۴۸ تا ۵۲ px موبایل، حاشیهٔ inline ۲۴ px. آیکون خطی ساده ۲۰ px؛ از ایموجی به‌عنوان آیکون خدمات استفاده نشود.

تصویر فضای اتاق نسبت ۴:۳، hero خانه در desktop حدود ۱۶:۹ با ارتفاع حداقل ۶۴۰ و حداکثر ۸۲۰ px. عکس‌های غذا contain با نسبت قاب ۱:۱؛ برای تصویر کوچک واقعی upscale زیاد نکن. کادرهای سفید عکس غذا روی surface روشن باشند؛ آن‌ها را روی زمینهٔ تیره با حاشیهٔ سفید تند نچسبان.

### ۵٫۴ حرکت

hover دکمه ۱۵۰ ms، drawer/dialog ۲۲۰ ms، reveal بخش حداکثر ۴۰۰ ms با جابه‌جایی ۱۲ px. هیچ اسلایدر خودکار، صفحهٔ ورود تمام‌صفحه، cursor سفارشی، صدای خودکار یا انیمیشن پیوستهٔ بزرگ نباشد. عکس hero ثابت است. `prefers-reduced-motion` تمام حرکت‌های تزئینی را حذف کند. محتوا قبل از اجرای JS هم دیده شود.

## ۶. قرارداد مسیرها، query و لینک‌ها

تمام مسیرهای زیر local هستند. دکمهٔ رزرو به سایت فعلی یا درگاه خارجی نرود. `href="#"`، دکمهٔ بدون رفتار، لینک به مرجع خارجی در nav مهمان و لینک شکسته ممنوع‌اند.

| شناسه | مسیر | نتیجه و CTA |
|---|---|---|
| ROOT | `/` | redirect به `/fa` |
| HOME | `/fa` | خانهٔ کامل |
| ROOMS | `/fa/rooms` | هشت نوع با فیلتر؛ کارت به slug خودش |
| ROOM | `/fa/rooms/[slug]` | یکی از هشت slug پیوست؛ نام ناشناس -> 404 |
| BOOK | `/fa/book` | فرم و خلاصهٔ نمایشی؛ query مطابق زیر |

| DINING | `/fa/restaurant` | معرفی کافه و رستوران |
| MENU | `/fa/restaurant/menu` | دسته، جست‌وجو و dialog محصول از query |
| CART | `/fa/restaurant/cart` | سبد و جمع اقلام نمایشی |

| ABOUT | `/fa/about` | معرفی مجموعه |
| FACILITIES | `/fa/facilities` | امکانات موجود در منبع |

| NOT_FOUND | مسیر نامعتبر | صفحهٔ 404 اختصاصی با لینک خانه، اتاق‌ها و تماس |

انگلیسی فاز پس از دمو است؛ فارسی زیر `/en` با `lang=en` رندر نشود. اگر مدیر بعداً ترجمهٔ کامل خواست، تمام مسیرها با dictionary واقعی locale توسعه یابند.

**Query رزرو:** `room=<slug>&checkIn=YYYY-MM-DD&checkOut=YYYY-MM-DD&adults=1&children=0`. تاریخ ذخیره‌شده ISO Gregorian روز تقویمی است؛ نمایش و انتخاب فارسی/جلالی. query ورودی parse و validate شود؛ بزرگسال ۱..۶ و کودک ۰..۳؛ تک‌اتاق حداکثر ظرفیت همان اتاق. ظرفیت کودک اضافه اختراع نکن؛ مجموع افراد از ظرفیت اعلام‌شده تجاوز نکند. مقدار نامعتبر با پیام قابل فهم اصلاح/پاک شود؛ هیچ تاریخ ساختگی خودکار تأیید نشود.

**Query منو:** `category=<ASCII-slug>&q=<text>&product=<numeric-id>`. نمونه: `/fa/restaurant/menu?category=plates&product=97818111`. product متعلق به دستهٔ دیگری بود دسته از دادهٔ محصول گرفته شود؛ q متناقض را برای بازشدن محصول نادیده بگیر. بستن dialog فقط product را از query حذف کند و scroll/جست‌وجو را حفظ کند. شناسهٔ پنهان/ناشناخته پیام «این مورد در منوی نمایشی در دسترس نیست.» بدهد؛ از API برای پیدا کردنش درخواست نزن.

**Query گالری:** `filter=all|rooms|restaurant|public|exterior&image=<asset-id>`. برای room filter جدید یک slug اختراع نکن؛ درون gallery کنترل جداگانه و data-defined باشد. query نامعتبر به حالت all برگردد.

## ۷. پوسته و اجزای مشترک

### ۷٫۱ Header

بالای hero خانه/رستوران: absolute، ارتفاع ۹۶ px، سه ناحیه؛ سمت راست دکمهٔ «منو» با آیکون، وسط wordmark «اورین / AVRIN HOTEL»، سمت چپ دکمهٔ «برنامه‌ریزی اقامت». روی عکس متن surface با پس‌زمینهٔ تیرهٔ ملایم برای خوانایی. در اسکرول بعد از ۸۰ px header به sticky height76 و سطح canvas/خط پایین تبدیل شود؛ پرش محتوا ندهد. صفحات فرم/منو از ابتدا header جامد داشته باشند. موبایل ارتفاع72؛ wordmark وسط، menu راست، رزرو کوتاه «اقامت» چپ.

## ۹. اتاق‌ها و صفحهٔ اختصاصی هر اتاق

### R01 — فهرست `/fa/rooms`

Hero حدود ۴۴۰ px desktop با stayHero و عنوان «اتاق‌های اورین»؛ در mobile ۳۴۰ px. intro دوخطی؛ فیلترها «همه / استاندارد / VIP» و ظرفیت «همه / ۱ نفر / ۲ نفر / ۳ نفر» با query `tier=all|standard|vip&capacity=all|1|2|3`. ترتیب پایه همان جدول هشت اتاق پیوست؛ filter هم‌زمان با AND. حالت صفرنتیجه با دکمه «پاک‌کردن فیلترها». بین نمایش همه و فیلتر، اسکرول ناگهانی به بالای صفحه رخ ندهد.

کارت اتاق در desktop row شامل عکس ۷ ستون و متن ۵ ستون، ردیف بعدی آینه شود؛ فاصله ۷۲ px. داخل متن: گروه، نام، ظرفیت/نوع تخت، توضیح کوتاه، «جزئیات اتاق» و «بررسی اقامت». نرخ خام در منبع به ریال است و یک نرخ VIP ناسازگاری دارد؛ این دمو **نرخ اتاق را نمایش/محاسبه نمی‌کند**. متن جای نرخ: «برای هماهنگی نرخ با پذیرش تماس بگیرید.»

آدرس «تهران، میدان انقلاب، کارگر شمالی، کوچه مجد، پلاک ۱۲». مختصات اصلی `35.70206906079886,51.39048134973817`. لینک مسیر: `https://www.google.com/maps/dir/?api=1&destination=35.70206906079886,51.39048134973817`. مختصات ناسازگار `merchantCities` برابر `35.70291,51.34976` مصرف نشود. فاصله تا فرودگاه، راه‌آهن و مترو یا مدت رسیدن را بدون اندازه‌گیری نساز.

فرم واقعی ارسال پیام در این دمو لازم نیست. یک پنل «برای هماهنگی با پذیرش تماس بگیرید» با تلفن و ایمیل کافی است. دکمهٔ کپی آدرس پس از کلیک از Clipboard API استفاده کند؛ اگر پشتیبانی نشد متن قابل انتخاب باشد. فقط بعد از موفقیت واقعی پیام «آدرس کپی شد» نشان بده.

### Q01 — پرسش‌های متداول `/fa/faq`

این شش پرسش با پاسخ کوتاه و پیوند مرتبط ساخته شوند:

1. «چطور اتاق‌ها را بررسی کنم؟» — صفحهٔ اتاق‌ها و برنامه‌ریزی اقامت نمایشی را معرفی کن.
2. «چطور رزرو واقعی انجام دهم؟» — تماس با پذیرش، با لینک تلفن.
3. «منوی رستوران کجاست؟» — لینک مستقیم منو.
4. «آیا سفارش این نسخه ثبت می‌شود؟» — توضیح کوتاه دربارهٔ نمونه بودن سبد.
5. «ساعت ورود و خروج چیست؟» — برای شرایط تأییدشده با پذیرش هماهنگ کنید.
6. «شرایط کنسلی چیست؟» — شرایط نهایی را پیش از رزرو از پذیرش بپرسید.

accordion امکان باز بودن چند پاسخ را داشته باشد. عنوان پرسش button با `aria-expanded` و `aria-controls` باشد. برای کودک، حیوان خانگی یا قانون کنسلی عدد و حکم حدسی ننویس.

### L01 — شرایط `/fa/policy`

عنوان «راهنمای شرایط اقامت». متن ابتدا «شرایط نهایی رزرو باید با پذیرش هماهنگ شود.» باشد. بخش‌های مدارک، ورود و خروج، کودک و کنسلی با پیام کوتاه هماهنگی ساخته شوند؛ متن قانونی و عدد ساختگی اضافه نشود. در گزارش داخلی وضعیت صفحه «قالب کامل؛ متن نیازمند تأیید مدیریت» ثبت شود. تاریخ تأیید یا نام مسئول حقوقی نساز.

### L02 — حریم خصوصی `/fa/privacy`

رفتار واقعی همین دمو را توضیح بده: سبد نمونه با شناسه و تعداد در مرورگر ذخیره می‌شود؛ برنامهٔ غیرشخصی اقامت در session است؛ فرم‌ها اطلاعاتی به هتل نمی‌فرستند؛ ردیابی و analytics پیش‌فرض فعال نیست؛ سرویس نقشه فقط پس از درخواست کاربر بارگیری می‌شود. دکمهٔ «پاک‌کردن دادهٔ نمایشی این مرورگر» فقط کلیدهای متعلق به همین پروژه را حذف کند و نتیجه را نمایش دهد. استفاده از `localStorage.clear()` و حذف تمام داده‌های مبدأ ممنوع است. متن حریم خصوصی سرویس‌دهندهٔ قبلی را منتقل نکن.

### E01 — خطا و صفحهٔ پیدا نشد

404 اختصاصی با wordmark، H1 «این صفحه پیدا نشد»، متن کوتاه و پیوندهای خانه، اتاق‌ها و تماس. خطای عمومی با متن «نمایش این بخش ممکن نشد»، اقدام تلاش مجدد و لینک خانه. stack، جزئیات داخلی و اطلاعات حساس در رابط نمایش داده نشوند. برای بارگیری واقعی skeleton هم‌اندازه بساز؛ تأخیر ساختگی برای نمایش انیمیشن ایجاد نکن.

## ۱۶. قرارداد داده و مرحلهٔ ورود منابع

یک ابزار محلی `scripts/import-avrin` فایل‌های اصل را فقط بخواند، دادهٔ مناسب برنامه را در `src/data` تولید کند و گزارش موارد پنهان یا نیازمند تأیید بدهد. اجرای برنامه بعداً به مسیرهای Desktop وابسته نباشد. فیلدهای استاندارد:

### قرارداد ذخیره‌سازی محلی

کلید سبد در localStorage برابر `avrin-demo.cart.v1` و مقدار آن `{schemaVersion:1,lines:[{id,quantity}]}` است. کلید برنامهٔ اقامت در sessionStorage برابر `avrin-demo.stay.v1` و کلید نمونهٔ سفارش `avrin-demo.order.v1` است. قیمت، نام، مسیر عکس و دادهٔ شخصی در ذخیرهٔ سبد نوشته نشوند؛ از دادهٔ محلی معتبر بازسازی شوند. parse شکست‌خورده یا نسخهٔ ناشناخته فقط همان کلید را کنار بگذارد. دکمهٔ پاک‌کردن در حریم خصوصی فقط همین سه کلید را حذف کند.

برای تحویل، کاتالوگ audit با همهٔ ۲۴۴ قلم نزد فایل‌های ابزار import باقی بماند؛ دادهٔ runtime منوی مشتری فقط ۲۳۴ قلم عمومی داشته باشد. منبع اصلی حذف نمی‌شود. متن نام و توضیح محصولات به شکل متن React نمایش داده شود؛ HTML خام منبع مستقیماً اجرا نشود.

## ۱۷. معماری فنی و ساختار پروژه

پایهٔ انتخابی: Next.js App Router، TypeScript در حالت strict، CSS Modules و فایل `tokens.css`. فاصله‌ها با CSS logical properties نوشته شوند. اگر پروژهٔ موجود Tailwind دارد از ابزار همان نسخه استفاده کن، با همان توکن‌ها و نسبت‌های این سند. قالب کامل آمادهٔ هتل وارد نکن. React Context و reducer برای سبد کافی است؛ پایگاه داده، Redux یا API سرور برای این دمو لازم نیست.

وابستگی‌ها محدود باشند: Next/React/TypeScript، ابزار build تصویر مانند sharp، یک primitive معتبر و دسترس‌پذیر برای Dialog و یک تقویم فارسی واقعی. طبق مستندات فعلی DayPicker برای نسخهٔ جدید از `@daypicker/react` و `@daypicker/persian` استفاده می‌شود؛ ورود `DayPicker` و `faIR` از `@daypicker/persian` است. اگر پروژه از قبل v9 دارد، مستندات همان نسخه را بخوان؛ مسیر import دو نسخه را مخلوط نکن. نسخهٔ نصب‌شده و lockfile ثبت شوند.

مستندات رسمی: [راه‌اندازی Next](https://nextjs.org/docs/app/getting-started/installation)، [Next Image](https://nextjs.org/docs/app/api-reference/components/image)، [تقویم فارسی DayPicker](https://daypicker.dev/localization/persian)، [تغییرات نسخهٔ ۱۰](https://daypicker.dev/upgrading). صرف ترجمهٔ اسم ماه‌های میلادی به فارسی، تقویم جلالی محسوب نمی‌شود.

D01 تا D06؛ منوی ۲۳۴ قلم عمومی در ۲۸ دسته؛ فیلتر، جست‌وجو، dialog با query، کارت بدون عکس، تعداد، C01 و C02. دادهٔ اصلی ۲۴۴ قلمی حفظ شود. آدرس‌های پرداخت سامانهٔ قبلی و کلید API نقشهٔ آن‌ها را به پروژه منتقل نکن.

### P5 — تکمیل صفحه‌ها

گالری، درباره، امکانات، تماس/نقشه، FAQ، شرایط، حریم خصوصی، 404 و redirect ها. صفحهٔ الزامی با متن «به‌زودی» قابل تحویل نیست. صفحهٔ شرایط با قالب کامل و پیام صادقانهٔ نیازمند هماهنگی پذیرش، وضعیت روشن و قابل بررسی دارد.

### P6 — بررسی و تحویل

lint، typecheck و build را مطابق ابزارهای پروژه اجرا کن. مسیرها را در مرورگر مرور کن. تست‌های معنادار برای photo-gate، formatter پول، قواعد روز تقویمی و اعتبارسنجی سبد بنویس و اجرا کن؛ تست‌های صرفاً تکرارکنندهٔ markup لازم نیستند. تصویری از اجرای واقعی خانه، اتاق‌ها، یک جزئیات VIP، معرفی رستوران، منوی عکس‌دار و بدون عکس، سبد، رزرو و تماس در موبایل و دسکتاپ ذخیره کن.

README شامل فرمان نصب/اجرا/پورت، وضعیت نمایشی و کارهای باقی‌مانده باشد. `CONTENT_REVIEW.md` ادعاهای منتظر تأیید؛ `ASSET_USAGE.md` اتصال اصل به URL عمومی و نقش عکس؛ `IMPLEMENTATION_STATUS.md` نتیجهٔ معیارهای زیر را ثبت کنند. screenshot ساختگی یا نتیجهٔ تست اجرا‌نشده را مدرک کار معرفی نکن.
